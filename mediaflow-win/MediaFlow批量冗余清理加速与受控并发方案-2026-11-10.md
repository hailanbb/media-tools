# MediaFlow 批量冗余清理加速与受控并发方案

2026-11-10 修订。本方案评审当前本地工作区的重复版本清理入口 `POST /api/archive/clean`。删除源季、删除整剧、归档和 MoviePilot 补缺各自具有不同的执行条件，本次提速只作用于重复版本清理。

## 建议决策

第一版合并删除后的两次目录读取，复用同一份真实目录做核验和诊断，保持删除串行。随后根据实际耗时决定是否增加跨季并发。65 季在 20～25 秒内完成可作为探索目标。原方案记录的 180～220 秒作为待复现基线，本次评审没有在真实媒体库重跑删除压测。

## 当前实现与能够兑现的收益

| 环节 | 代码核查结果 | 对决策的影响 |
|---|---|---|
| 页面调度 | `frontend/index.html` 的 `confirmReviewDone` 为每季发一次请求，共用的 `runBatchPipeline` 串行执行并在每项后等待 100 ms | 65 项固定等待合计约 6.5 秒。HTTP 请求可能复用连接，握手耗时须单独测量。仅调整清理入口的等待或调度参数。 |
| 目录读取 | `app/api/archive.py` 的 `clean_duplicates` 在制定计划前强制读取。至少一个文件删除成功时，先刷新一次、丢弃返回值，再强制读取一次做诊断。无需清理的季会提前返回 | 成功删除的季可以从三次强读降到两次。假设 65 季都发生删除，单次强读确为 500 ms，串行路径可少 65 次读取，约 32.5 秒。这是估算。 |
| 删除与日志 | 每个文件单独删除并捕获异常。一季只要有一项成功，操作日志就可能写成 completed，随后诊断失败仅记警告 | 先区分全部完成、部分完成和结果待核实，再引入并发，否则页面会更快地给出错误结论。 |
| 季度状态 | 清理后遍历本层所有视频的集号，调用 `diagnose_season`。此路径未同步写回缺集列表，也没有完整复用初检的正片筛选和归档覆盖核对 | 清理前后的判定口径需要统一，尤其是花絮、零字节、跨季文件、两库合计已齐和综艺分段。 |
| 汇总与落库 | 清理接口已接受多个记录 ID，按受影响任务重算汇总，然后提交。页面逐季发请求时，同一任务可能反复全量统计。本机数据库只读查询得到 `journal_mode=delete` | 先优化汇总查询及事务范围。启用 WAL 仍然只有一个写入者，不宜据此承诺零锁等待。 |

## 分阶段实施

### 第一阶段：减少重复读取，纠正结果口径

1. 将清理前目录清单用于生成计划。清理后只强读一次，同一返回值用于核对实际删除、检查保留文件及重新诊断。内存差集可用于显示进度；存在外部入库、同名替换或请求超时时，须以重新读取的实物为准。
2. 复用初检对本季正片、集号和归档覆盖的规则，一次更新识别集、重复集、缺集和状态。删除已发生但核验失败时记录“待核实”，保留成功文件和失败文件清单。只有核验通过才允许进入可归档。
3. 先处理待删视频，再处理仅属于已确认删除视频的伴生文件。主视频删除失败就保留对应附件。字幕、全局海报、共享附件和保留版本始终排除。批量执行沿用原有 force_clean 的用户选择。
4. 独立记录每季列目录、生成计划、删除、末次核验、数据库写入和前端等待耗时。若第一阶段已达到实际使用要求，可以在此停止。

### 第二阶段：限制整个服务的请求量

优先跨不同源季并行，单季内部先保持顺序。初始可试两个季同时处理，CD2 删除全服务一次只发一个，借其他季的读取和诊断填补等待。两者是压测起点。若实测删除排队占主导，再试全服务两个删除槽位，每次只改一个参数。

- **并发与速率分别控制。** 三个浏览器工作槽乘每季四个删除槽，单页可同时发出 12 个删除请求，多个页面还会叠加。后端按同一账号或挂载共享删除上限，并设置请求发出间隔。读取和重试也计入调用统计。进程内信号量只覆盖一个进程，多进程或多个实例共用挂载时，需共用执行器或统一限流。
- **同一季串行。** 按规范化源季路径认领任务，避免两个不同记录 ID 同时清理同一目录。与归档、源目录删除等会修改同一路径的操作互斥；整剧操作还要检查父子路径冲突。预览后文件发生变化时重新计算计划，新增的待删文件应重新展示后再执行。
- **限流与超时分别处理。** 明确限流时暂停发新请求，遵从服务端提供的等待时间，退避后先以单并发恢复。删除请求发出后丢失响应时，先核对路径、文件身份及保留集，再决定是否继续。需同时检查 CD2 客户端底层重试，避免在业务层核对前已重发删除。
- **短事务写入。** 网盘等待放在数据库写事务之外，每季结果和操作日志一起提交。以数据库按任务和状态分组计数替代加载所有季度对象；合并同任务的汇总刷新，批次收尾再校准。数据库忙时只重试结果写入，禁止连带重放云端删除。

### 第三阶段：按实际需要增加后台批次

若只需缩短等待，保留现有接口和页面即可。若要支持浏览器关闭后继续、多个操作者查看进度或服务重启恢复，建议增加后台批次：页面提交一次获得批次 ID，后端保存逐季计划、执行结果和操作标识，页面按批次查询进度。原单季入口复用相同执行逻辑。

重复提交同一操作标识返回已有进度。取消后停止领取新季，已发出的删除完成核验再结算。重启后只恢复可确认的步骤，结果不明的文件进入核验。页面分别统计完成、部分完成、无需清理、失败及待核实，保留各季详情。

## 验收与回退

| 验收项 | 通过标准 |
|---|---|
| 正确性 | 对相同初始目录，串行版与优化版产生相同的保留集。以初检结果校验识别集、缺集和状态；模拟删除后新增正片、被保留文件消失和目录读取失败，均不得误报齐全。 |
| 部分失败与重入 | 模拟第 N 次删除失败、服务端已删但响应超时、同名文件替换、云端成功后数据库写入失败、两页重复点击。核对实际删除清单、附件依赖、操作日志及最终状态，恢复后无重复删除。 |
| 负载边界 | 同时启动两个批次，记录全服务在途删除峰值及每秒请求量，验证配置上限。注入限流后检查退避、降并发、取消与恢复。 |
| 性能 | 在可重置测试目录用同一份 65 季清单分轮比较串行基线、去重读取、跨季并发。记录实际删除文件数、强读次数、总耗时、单季 P50/P95、限流次数及数据库等待。每轮还原相同文件集，区分冷、热缓存，避免把第二轮无文件可删算成提速。 |
| 回退 | 发现保留集不一致、频繁限流、待核实项增加或数据库汇总失真，停止派发新项，完成在途核验。并发配置退回 1，保留操作记录；已经发生的删除不能靠切换程序版本撤销。 |

建议先交付第一阶段的对照数据，再决定并发预算和端到端耗时目标。本次交付为方案修订，未实施清理或并发改造。
