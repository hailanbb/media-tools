## 一、目标与规则优先级

用户完成初检后，应能通过一次批量执行完成有明确依据的整理，少数必须裁决的事项按独立问题集中处理。系统负责补齐资料、识别内容、制定操作计划、执行后核验并更新分类。每个处理结果展示实际去向。

本方案覆盖此前方案中与以下规则冲突的规定。

| 项目 | 本轮确定的规则 |
| --- | --- |
| 优先处理 | 有源端多余副本、同 ID 目录归并或归档已齐待清源动作的作品季，优先进入「待复核清理」 |
| 连载季副本 | 已确认同一期、同一段、同一内容版本的稳定副本可以清理，保全该季仍需留源的内容 |
| 目录归并 | 同 TMDB ID 按该 ID 最新规范名称自动确定目标，归并纳入待复核清理 |
| 归档已齐清源 | 归入待复核清理，核验通过后执行「删除源端（本季）」 |
| 异常处理 | 处理身份、编号、资料冲突，以及明确的读取或执行失败，给出可完成的动作 |
| 用户修正 | 单季修正保存后按展示的计划修正目录、文件、关联资料和记录，核验后重新分流 |
| 补缺模块 | 显示名统一为「缺集待补」，移除该模块的「删除源端（本季）」及其批量入口 |
| 站点规则类型 | 自动确定动漫／非动漫规则，取消强制类型选择和「⚠️ 类型待确认」 |
| 页面顺序 | 待复核清理 → 异常剧集 → 缺集待补 → 连载留源 → 齐全可归档 |
| 操作方式 | 默认一次性初检与批次处理，运行结束即结束本轮，不建立“系统跟踪”待办或常驻网盘轮询 |

页面顺序按用户给出的处理流程排列，并将连载留源置于齐全可归档之前。模块切换、汇总卡、移动端、结果摘要采用同一顺序。

## 三、全局数据与分流设计

### 3.1 先形成事实，再决定动作和模块

每个作品季建立同一份可复用的分析结果，至少包含以下信息。

- 身份事实包含 TMDB ID、目标季、有效别名、适用豆瓣条目、已有人工修正和有冲突的具体文件。
- 内容单元包含作品、季、期／集、段、内容类别、剪辑版本及其实际文件。技术编码版本单独保存。
- 实物覆盖分别保存源端、归档、可信媒体库明细，注明读取是否完整以及已知空目录，不能用读取失败表示零覆盖。
- 播期分别保存已播、未播、播毕、未知及来源，总期数和播毕分别取证。
- 操作清单包含可清理副本、可归并目录、可清源范围、需修正文件和每项完成后的去向。

旧 `status` 仅用于迁移和历史展示。最终模块由本次可执行或待裁决的动作、播期、覆盖共同计算，避免保存一条旧状态后被多个模块重复解释。

### 3.2 主模块优先级

| 顺序 | 条件 | 主模块及处理 |
| --- | --- | --- |
| 1 | 有待处理的源端副本、同 ID 规范化归并、归档已齐待清源 | 待复核清理，集中展示计划。存在具体争议的部分就地标明，其他已证实动作可以先完成 |
| 2 | 清理前置工作完成后，仍有身份、内容映射、关键资料或实际操作问题影响后续结果 | 异常剧集，展示具体问题并自动补证或执行已明确的修正 |
| 3 | 已确认正在连载或待播 | 连载留源，展示已播未收情况，按当前产品规则等待该季可补缺阶段 |
| 4 | 已播毕且有确认缺口，包括源端无视频、归档也未覆盖 | 缺集待补，按缺失内容单元搜索并推送 |
| 5 | 已播毕、覆盖齐全、清理和修正动作均完成 | 齐全可归档 |
| 6 | 源端已清除且归档保留验证通过，或已归档完成 | 完成记录，从当前待办退出 |

导航顺序用于用户操作。播期判断在下载资格判断前执行，避免把未播内容误推为缺集。

有副本信号的季先进入待复核清理。自动分析确认它们属于不同内容后，该项记为“多内容版本均已保留”，直接重新分流。无法解释的文件转入异常时保存已经完成的判断和文件指纹，同一证据下不再次被原“重复集号”送回清理模块。新文件或新事实出现才重新评估相应内容。

作品季仍只保留一张主卡，跨季目录计划采用组级任务，列出影响的季。汇总分别展示作品季数、目录组数、文件数和可回收容量，避免相加重复计数。执行中的事务有独立进度，失败或未知回执继续显示真实状态。

## 四、待复核清理承担的三类工作

### 4.1 同内容副本清理

清理必须先判定内容等价，再选择保留副本。

| 比较维度 | 清理约束 |
| --- | --- |
| 作品、季、期／集 | 身份与编号映射一致，同一个数字在不同发行口径下不能直接比较 |
| 段 | 上、中、下或 Part 标记分别表示内容，整期替代分段需要完整包含的证据 |
| 内容类别 | 正片、Vlog、加更、纯享、彩蛋、先导、采访等各自成组 |
| 剪辑版本 | 普通版、加长版、删减版、平台专属内容各自保留，确认完全等价后才允许互相替代 |
| 技术副本 | 同内容组内按可播放性、用户质量偏好、分辨率、兼容性、音轨字幕和编码进行选择 |

用户接受的基本案例固定作为验收样本。《中餐厅》S10E01 普通 H.264 与普通 H.265 可比较，Vlog 和加更各自保留。《你好时光》普通版和加长版分别保留。

文件名标记、可信 NFO、发行来源与编号映射、文件时长、音轨字幕共同提供依据。文件字节校验可证明完全相同的副本。不同编码的等价性需组合证据，单独依赖集号、大小、分辨率或时长不能认定。需要补充 MediaInfo 时仅读取有争议的候选，并缓存稳定文件的结果，避免对整个媒体库反复探测。

某季有一组上下段或子目录，不应阻止另一组已证实的完全相同副本清理。未知内容保留并明确到文件。预览必须列出“删哪个、保留哪个、为什么可替代”，实际执行使用同一计划及证据版本。

连载季允许处理已完成、稳定且无活动下载／做种路径依赖的同内容副本。遇到活动写入只延后相关文件，其他组继续执行。完成后回连载留源。归档跨库移动仍按播毕与覆盖条件执行。

外挂字幕和独有音轨需要随保留内容保存，刮削附件按关联视频更新。无关联依据的 NFO、图片保留，不因视频名无法解析就当作可删孤儿。

### 4.2 同 ID 自动规范名称与目录归并

对同一受控分类范围内、相同 TMDB ID 的目录，系统读取该 ID 当前条目的简体中文名称，按“规范剧名 (作品首播年) [tmdbid=ID]”确定规范目录名。首播年采用作品层年份，季年份记录在季资料中。名称缺失时依次取有效中文别名、原名和现有名称，注明本轮采用依据。

现有目录名一致时直接使用。全部不一致时自动新建规范目录，把本次组中相关内容按季归并。名称做文件系统字符规范化，保留 ID 区分同名作品，并处理大小写等价路径。读取最新名称失败时保留原路径，本轮已具备依据的副本清理继续完成，命名任务记录具体读取失败。

相同目录 ID 是默认归并依据。若文件自身存在明确异 ID 或作品／季归属冲突，系统先隔离争议范围，其他季正常处理。仅拼音、英文译名、发行组前缀不同不会自动判为另一作品。

| 路径角色 | 具体行为 |
| --- | --- |
| 源端主目录 | 在当前受控源库分类下归并，正在连载的文件继续位于源库 |
| 未来归档目录 | 按同一规范名确定目标，由后续归档动作使用 |
| 已存在的别名归档目录 | 纳入同 ID 覆盖核验。需要统一实物名称时作为独立归并步骤列入同一计划，仅处理本次核实的目录与季 |
| 目标季目录 | 按真实季号建立或复用 Season N，不按目录名称猜改季号 |

已有目标同季文件前缀一致时使用其有效季集标记 `SxxE…` 前的前缀。无目标文件时由规范剧名和项目命名格式生成。目标存在多种前缀时，自动优先采用与规范名称一致的模板，再采用数量最多的有效模板，同票采用确定的项目格式，在计划里展示选择依据，无需用户逐文件选名。

新建规范目录的例子为 `规范剧名 - S01E01 - 原发行信息.mkv`。本次只统一季集标记前的展示前缀，标记及之后的集号、发行信息、分段和版本信息原样保留。旧剧名在后缀中出现时继续保留。字幕、分集 NFO、缩略图使用对应新基名并保持语言标记。

全名碰撞先比较内容。已证实等价副本按清理规则处理；不同内容优先保留能区分内容的原前缀，仍碰撞时放入计划中明确列出的保留子目录并标记后续规范化事项。不能覆盖文件，也不能通过全局修改 S 后文本消除碰撞。

剧根海报、NFO、字幕、未知文件以及其他季须逐项纳入迁移或保留清单。公共附件发生碰撞时保留源版本于具名附件目录。旧目录完整迁出、实际复读为空后再删除空壳，刷新原目录父级、目标父级和页面。仍有未处理季或附件时保留旧根，并按实际结果显示剩余内容。

同一个目录组只需要一次批量授权。元数据读取、选名、新建、移动、改名、附件保全、空壳清理、刷新和重新分流连续执行。并发下载器可能写入旧路径的任务需检查路径依赖，明确依赖的部分单独延后或使用已支持的路径更新能力，不能只移动媒体后丢失下载器关联。

### 4.3 归档已齐后的源端清理

该入口完整迁入待复核清理。系统核验目标作品季、正片内容覆盖、实际可用文件及源端独有内容。普通版已归档不等于源端加长版、Vlog 也已保存，独有内容须先完整归档或留源。

计划通过后提供「删除源端（本季）」，允许多个已通过计划一次批量执行。顺序为独有内容保全 → 目标实物核验 → 源季回收 → 空壳检查 → 刷新剧集所在父目录及相关季目录 → 结案。仅剩空根时可以清理空壳，有其他季或内容则保留。

回执显示“源端已清理，归档已保留”，该季从待办退出，并在完成记录可查。回收失败和刷新失败分别记录与重试，不能用数据库标记替代实际删除成功。

## 五、异常剧集的自动解决与人工修正

### 5.1 用具体问题驱动自动补证

异常模块的默认卡片应解释“哪个事实导致哪个动作无法完成”。取消“证据待决 · 安全保留”和“系统跟踪”的主分类文案。可使用“集数口径待核对”“季号与作品不符”“资料读取失败”“文件内容待识别”“修正未完成”等具体名称。

系统在初检及本次处理批次中完成有界自动补证，优先复用有效的同季资料和用户给出的条目链接。步骤包括精确作品 ID、季名／季年份、独立豆瓣季条目、可信 NFO、原发行标题及必要的文件属性。只为缺失事实请求数据，避免每季重复搜索同一作品或重跑全部初检。

相同作品的多个季不能互相借用总期数、播毕或文件覆盖。主目录括号中的首播年不应排除后续季年份正确的豆瓣条目。当前可读取的资料未被匹配、返回未解析、解析成功未采用、缓存命中旧错误等情况都要记录阶段与原因，以便修正数据接入链路。

自动补证成功立即重算，必要时继续执行本批已授权的清理或修正步骤。若有确实无法取得的关键事实，显示一个具体问题与最小输入，例如贴一个季条目链接或选择正确季号。用户可以跳过本轮，跳过项进入处理记录，不占默认人工待办计数。新一轮初检仍正常分析，有新证据时更新结果，不创建后台“系统跟踪”任务。

### 5.2 豆瓣与 TMDB 按事实合并

资料融合分别解决身份、总期数、分段映射和播毕。豆瓣同季明确有总期数时参与判定；TMDB 有分段名和逐集日期时提供期段对应。不能让 TMDB 某条加更或衍生内容没有日期，否定已经核实的整季正片播毕。

用户提供的 URL 自动提取 subject ID，读取后核对作品、季号和季年份，保存为可复用的季条目绑定。详情中直接展示采用哪些资料及得到什么结果。条目总期数与正片发行编号一致时采用整期口径；存在明确上下段时建立段映射。总数比例达到 1.5 倍或 2 倍仅可作为核对线索，须由内容标题或发行证据落实映射。

数据字段缺失记录为未知，不能写成未播毕。季级完结证据优先使用对应季的明确完结状态、终期发行与完整排期或有效人工确认。作品整体 Returning Series 不妨碍已结束的旧季归档。总数已知、身份已明时自动继续查找季终依据，不要求用户逐季手填整张表。

同一来源返回合成的 1…N 集号列表仅证明来源提供了数量，不能当作真实分集内容表。采用普通版、加长版、上下段哪一种覆盖都须与其编号解释一致，不能混算几个体系。

### 5.3 人工确认后完成实际改名和分流

保留「人工确认」入口。在「若当前目录归属有误，点此展开单季修正选项」中，用户填写正确作品 ID／豆瓣条目、季号、必要编号映射和资料后，系统自动生成具体修正预览，展示新剧名、目标目录、文件名变化和预计模块。

主按钮沿用「保存确认并更新结果」，按钮附近写明本次将执行的目录和文件修正。一次确认后按“保存修正依据 → 生成固定执行计划 → 实物改名／移动 → 附件及关联资料更新 → 核验 → 分流”的流程完成。

| 用户修正内容 | 文件与记录变化 |
| --- | --- |
| 只确认现有作品正确、总数或播毕 | 更新对应事实并重算，确有名称规范化需求时展示并执行命名计划 |
| 同季作品 ID 或规范名称修正 | 创建／复用正确剧目录，迁入本季，统一前缀，更新目录 ID 与属于本季的已知 NFO 身份字段 |
| 季号修正 | 按确认的映射调整 Season N 与文件中明确表示季号的 S 标记，保持集号和其他发行文本；预览明确列出例外变化 |
| 集号映射修正 | 只修改已明确确认的期／集／段映射，逐文件展示旧新对应，保留原编号审计 |

普通目录合并保持 S 后内容的约定适用于身份与季号未变的情形。用户明确纠正季号或集号时，按该修正更新相应标记，不能只改目录却留下错误 SxxEyy。复合文件名中重复出现的季集标记须由解析器判断指代关系，无法确定的标记保留并报告，禁止全局字符串替换。

单季修正仅作用于该季。旧剧根还有其他季时，建立新剧目录并移动本季。剧根 `tvshow.nfo` 共享字段不能被本季改绑覆盖到其他季。分集 NFO 采用结构化编辑，保留用户备注及无关字段，其他媒体、字幕和附件按文件关联迁移。

同时迁移目录组关联、有效人工确认、分段映射、补缺台账和下载／整理回执。身份改变时保留原请求身份与新身份之间的明确关联，避免重发已受理下载。文件迁移部分失败时显示已完成与剩余步骤，保持“修正未完成”，恢复后才展示最终去向。

### 6.1 附件目录与实际缺片

NFO、海报等刮削文件可提供作品、季、集、标题和来源线索，文件数量不计入正片实存数。系统通过完整目录读取、受控子目录发现及源归档／媒体库核验，区分以下结果。

| 实际结果 | 路由 |
| --- | --- |
| 已播毕，源端只有附件，归档与可信媒体库均未覆盖，身份和应有内容已知 | 缺集待补，可全季补缺，保留附件用于整理 |
| 已播毕，源端只有附件，归档正片完整 | 待复核清理，迁移独有附件并清理已无必要的源季 |
| 有未识别视频、可用性不明的 STRM 或未读完的内容子目录 | 定位具体文件或范围自动识别，不能直接当作无视频下载全季 |
| 目录不存在且有可靠历史记录，或确实为空 | 按其他端覆盖和播期计算缺口，明确不存在与读取失败的差别 |
| 目录读取失败 | 异常显示读取失败及可重试范围，成功后继续原计划 |
| 尚在连载或待首播，只有附件／先导 | 连载留源，展示真实播出情况 |

## 七、动漫规则自动选择

保留动漫和非动漫两套启用站点及优先级。类型判断由系统完成，主卡、单季推送、批量推送均取消强制“类型待确认”按钮和选择框。

**先根据初检目录名称及完整路径建立默认规则。** 这一步在读取任务时即可完成，元数据类型字段缺失或接口暂时不可用时，继续采用已有目录依据。初检选择到剧集目录或 `Season N` 时，向上找到最近的有效分类目录；初检选择到混合总目录时，按每部作品所属子目录分别判定。

| 目录／路径中的分类信息 | 自动采用的默认规则 |
| --- | --- |
| 动漫、动画、国漫、日漫、国产动漫、日本动漫、欧美动漫、Anime、Animation 等明确分类目录 | 动漫规则 |
| 综艺、真人秀、脱口秀、真人剧集等明确分类目录 | 非动漫规则 |
| `动漫/日本/作品名/Season 1` | 继承上级“动漫”，采用动漫规则 |
| `电视剧/综艺/作品名/Season 4` | 采用最近明确分类“综艺”的非动漫规则 |
| 电视剧、媒体库、下载、待整理等宽泛或混合目录 | 继续检查作品所在子目录、剧集目录名称、文件名中的明确类型标记及有效作品资料 |

目录匹配采用分类名称及明确词组，兼容简繁体和英文大小写。按路径层级从具体分类向上查找，不能因为祖先路径有“电视剧”就覆盖“动漫”子目录，也不能把片名偶然含某个字当成分类标签。文件名的明确类型标记作为补充线索，标题语言、国家和发行组本身不决定动漫类别。

在目录默认值上应用作品级证据，优先级为用户既有有效设置 → 已核实同作品的元数据／可信 NFO 类型 → 最近明确分类目录 → 剧集目录名、文件名及已取得标签的综合判断。若“综艺”目录中误放一部有明确动画类型资料的作品，该作品自动使用动漫规则，其他作品继续采用目录默认值。详情写明“根据初检目录‘动漫’采用动漫规则”或具体作品依据，保留自愿修改入口。

删除无依据时统一归入非动漫的兜底。目录及文件信息均无类型线索时，系统定向补取该作品资料并复用有效历史分类；取证请求实际失败时记录具体读取失败及恢复步骤，不生成强制“类型待确认”选择项。两套规则仍各自遵守已勾选站点范围。

同一批次逐作品固定类型与规则快照，后续识别更准确时应用于新批次。已受理下载继续对账。保存的人工修改按作品复用，不要求下一次初检重复选择。

## 八、缺集待补、连载留源、齐全可归档

### 8.1 缺集待补

统一替换所有可见“真缺集待补”为“缺集待补”，覆盖导航、计数、弹窗、批量结果、帮助文案和服务端展示信息。内部 `download_needed` 等兼容标识按迁移需要保留。

该模块提供推送补缺、重新搜索、查看详情／进度、核对入库等动作。移除“删除源端（本季）”、其更多菜单项、对应快捷键与批量入口。源端清理集中在待复核清理，并通过适用资格执行。旧客户端直接调用删除接口时也须校验资格，避免隐藏按钮后仍能从待补记录绕过。

源端为零正片且应有内容明确的已播毕季，可以正常进入该模块。下载目标来自未覆盖的内容单元，按期或段展示，避免把刮削文件、加更或已在途内容视为缺失正片。仅因本轮站点无资源仍留在待补，保留搜索结果。

### 8.2 连载留源

放在齐全可归档之前。该季有真副本或目录归并任务时，先在待复核清理完成相应工作，再自动返回连载留源。清理允许范围精确到已证实可替代的稳定副本，不能借此删除尚未保全的独有内容。

未知播期在补证期间显示具体资料问题，不能用“连载”掩盖未知，也不能把 `season_finished=False` 一律显示成已确认在播。

### 8.3 齐全可归档

仅展示正片覆盖完整、播毕已核实、当前清理及归属修正已完成的季。加长、加更、Vlog 等保留内容随计划归档，并保持内容区分。源归档两端互补时按同一内容单元取并集，实际归档确保目标最终完整，不能只依赖一个合计数。

## 九、批量交互与可靠执行

工具栏提供「执行推荐处理」，预览列出目录归并、同内容副本清理、归档已齐清源及用户已确认修正的实际范围。用户一次确认后逐项执行，系统完成刷新与分流。初次或新的删除范围必须在该预览内可见，初检本身负责分析和生成计划。

每张卡只显示当前需做的动作、影响文件数和处理后去向。存在多个动作时显示组内进度，避免用户完成改名后还要分别点刷新、核算、切换模块。信息示例为“保留普通版、加长版各一套，清理 3 个重复副本，完成后进入齐全可归档”。

执行计划持久化计划 ID、规则版本、文件稳定标识／大小／修改时间、源目标路径、内容覆盖证明和逐步骤回执。执行前局部复核文件变化，同作品季及相关物理路径互斥，冲突时只重算受影响部分。计划范围扩大或出现新的删除对象时回到更新后的预览，避免执行超出用户看到的范围。

每一步实际完成后记录回执。超时先对账实际路径再决定重试。重启恢复、重复点击和多窗口不能重复移动／删除。同一操作有部分失败时保留已完成部分及剩余动作，不能提前计为成功或重做全部步骤。优先使用可回收的删除能力，并记录提供方实际回收语义。

最终只读后验必须确认被保留的内容仍可访问、移动文件在正确目标、清理对象确已消失。刷新涉及的季目录、旧新剧根父目录和前端统计。清理成功而刷新失败单列为收尾失败，只重试刷新。

每个批次结束显示四类去向：进入缺集待补、进入连载留源、进入齐全可归档、源端已清理并完成。仍未解决的具体异常和本轮主动跳过项另列，保留失败原因和恢复入口。不能为了得到一个去向而制造播毕、齐全或删除成功结论。

升级时先对旧任务做无写入的重新解释，保存原始记录，生成新分类和待执行计划。旧人工确认、季映射、目录选择及已受理下载保持可追溯。重新解释不自动执行媒体移动或删除，用户看到新计划后通过批量入口执行。

旧 `period_review`／`archive_check` 不直接映射为某一个新模块，按无视频、分段、资料缺失、在播等具体事实重新判定。旧“已确认目录”表示的授权范围也须保留，不能将过去只保存目标的点击解释成新归并计划的执行授权。

本方案覆盖旧异常方案的“归档已齐清源留在异常”“确认只保存不改名”等相冲突职责，也覆盖旧补缺站点方案中强制“类型待确认”的规则。其他历史方案保留版本记录，实施时以本方案对应条款为准。

## 十一、验收标准

验收先对真实任务快照和完整只读文件清单生成新计划，审核内容等价和分流差异，再在隔离测试目录验证实际操作。当前 27 季清理和 123 季异常的数量不能作为新版需要人工处理的数量。应记录自动解决项、用户独立决定次数、未解决原因、误删为零及重复提示次数，验证这次改造确实降低人工工作量。

## 十二、实施顺序

1. 统一内容识别和覆盖判断，修复普通版与加更／加长／Vlog 互相淘汰的问题，建立预览和执行共用的计划。
2. 修复多源资料合并、分段及只有附件的结果，落实用户提供的季条目绑定与具体案例回放。
3. 调整清理优先分流，把目录规范化归并、归档已齐清源集中到待复核清理，完成结果自动转移。
4. 完成人工修正的实际文件处理、跨模块关联迁移和批量恢复，减少逐季重复操作。
5. 更新自动动漫规则、缺集待补名称、删除入口、模块顺序及旧任务兼容，执行 G01–G28。

全部阶段以 v2.5.44 的实际代码为基线实施。本文版本表示方案基线，不表示上述重构已经上线。
