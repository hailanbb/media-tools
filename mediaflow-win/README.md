## 💡 痛点直击与核心价值

在搭建基于 **115网盘 + CloudDrive2 (CD2) + MoviePilot (MP) + Emby/Jellyfin** 的现代家庭影院过程中，影视收藏者和影音玩家普遍面临一系列顽固痛点：

* 💥 **网盘同名碎片与目录撕裂**：115 网盘在 CD2 虚拟挂载下，多次下载极易生成 `(1)` 动态数字后缀；同剧因刮削差异被分裂在多个同名或错名目录下，常规批处理脚本极易误删或引发读写假死。
* 🔍 **刮削口径冲突与误报死锁**：TMDB 与豆瓣元数据冲突、正片与加长版、加更纯享特辑（E00/SP）及多集分段（Part1/Part2）混杂，传统逻辑经常误判“缺集”或“超集”。
* 🔄 **盲目补缺死循环与爆盘**：缺乏精细化做种门禁与站点分类路由，补缺任务盲目拉取超大体积未洗版整包，冲垮网盘配额并引发洗版死循环。
* 🛡️ **误删焦虑与收尾困难**：担心自动化清理误删源端独有的外挂字幕、高清海报、NFO 元数据或珍贵特辑；在网盘外部手动删除文件后，系统产生大量僵尸条目。

**MediaFlow (media-tools)** 采用首创的 **「清理优先」四维内容等价建模**，以**确定性状态机**驱动媒体整理全生命周期，配合严苛的 **G24 物理指纹双向核验**，彻底终结媒体库混乱，实现零数据丢失、高吞吐、可追溯的影视自动化治理。

## 🌟 五大核心治理模块

### 1️⃣ 待复核清理 (Review & Clean)
* **四维内容等价模型**：严格区分「普通正片」、「加长版/导演剪辑版」、「Vlog/加更/纯享/E00特辑」与「上下分段 (Part1/Part2)」，同内容组内择优去重，坚决防止不同剪辑版本相互循环覆盖。
* **同 TMDB 多目录规范归并**：自动识别同一作品在网盘中产生的多套碎片目录，支持选择标准目标路径并完成一键原子合并，多季一次性规整。
* **执行推荐处理 (Recommended Execute)**：后端采用受控信号量并发（`Semaphore(10)`）与大批次异步作业轮询，前端配备实时分步进度条，秒级输出处置结论并安全执行。

### 2️⃣ 异常剧集 (Anomaly Shows)
* **统一「手动复核」面板 (v2.5.61 重磅整合)**：将原先分散的重验、改绑、暂不处理收拢为一体化复核工作台，支持集中重核资料与文件、更正季号/总集数、以及可安全恢复的「暂不处理」。
* **五模块源目录对账 (v2.5.61 新增)**：当用户在 CloudDrive2 或 115 外部手动删除了网盘目录时，点击「核对源目录」即可按需发起父目录强读对账，自动核减已消失路径并更新任务统计，彻底告别“已删目录仍卡在列表”的尴尬。
* **双向元数据融合取证**：整合 TMDB 官方元数据与豆瓣多渠道网页/接口搜索，智能处理嵌套详情并保留可读诊断报告，消除外文译名误报。

### 3️⃣ 缺集待补 (Gap Filling)
* **动漫 / 非动漫独立站点规则**：补缺管理中深度隔离动漫（Anime）与常规影视（Non-Anime）两套独立的站点规则。支持双页签独立排序、独立开关，杜绝全站无限制盲目搜索。
* **严谨瀑布流选种决策链**：严格遵循「硬条件门禁 $\to$ 整包/散集阶段 $\to$ 站点优先级 $\to$ 同站做种档位 $\to$ 同档容量 $\to$ 稳定键」决策树，确保优先拉取高分优质种。
* **整季回退与综艺全集识别**：缺集 $\le 3$ 优先补散集；散集资源匮乏时智能回退整季合格包；按期综艺支持总数匹配的 Complete 声明整包识别。
* **无合格资源独立页签**：对于全网无合格种子的作品独立分流归档，支持单季及批量主动放弃删源预览，严格经过执行前指纹复核与幂等回执。

### 4️⃣ 齐全可归档 (Ready to Archive)
* **核对入库全量实物复核 (v2.5.58+)**：下载完成后点击「核对入库」，自动衔接完整物理实物复核，复用初检标准重新计算新副本、新内容版本与归属证据，绝不武断将虚假补齐的季直接归档。
* **独有资产与附件原子保全**：清源前自动将源端独有的加更、特辑、NFO 以及剧根/季级纯附件目录保全至归档库，杜绝误伤外挂字幕与刮削资产。
* **双端强读后验**：目标端入库核验成功且源端目录确认物理消失后，才生成完成回执并标记结案。

### 5️⃣ 连载留源 (Ongoing & Seeding)
* **追更动态追踪**：通过 TMDB + 豆瓣播出日历精确界定“已播缺集”与“未播待映”，未播集目绝不冒充缺集推送下载。
* **做种任务绝对保护**：处于 PT 做种周期或连载活跃期的视频严禁发起删除，安全留源观望，整季播毕齐全后自动流转至归档候选。

## 🚀 快速启动与部署

MediaFlow 支持 **Windows 原生直接运行** 与 **Docker 容器化部署** 两种方式，满足个人 PC 工作站与 NAS 服务器的不同需求。

### 方式一：Windows 原生免环境运行（推荐 PC / 工作站）

无需安装复杂的 Docker Desktop，直接使用原生 Python 进程运行，与本地 CloudDrive2 挂载盘性能契合度最高：

1. **获取代码并进入目录**：
   ```powershell
   cd media-tools\mediaflow-win
   ```

2. **配置运行环境 (Python 3.11 或 3.12)**：
   ```powershell
   python -m venv .venv
   .\.venv\Scripts\Activate.ps1
   pip install -r requirements.txt
   ```

3. **配置环境变量**：
   ```powershell
   copy .env.example .env
   # 使用记事本或编辑器修改 .env 中的 CD2 / MoviePilot 地址与密钥
   ```

4. **一键启动**：
   * **快捷启动**：双击运行 `启动本地服务.bat`
   * **命令行启动**：
     ```powershell
     python -m uvicorn app.main:app --host 0.0.0.0 --port 8080 --reload
     ```
   打开浏览器访问：`http://localhost:8080` 即可开始使用。

---

### 方式二：Docker 容器化部署（推荐 NAS / Linux 服务器）

针对群晖 Synology、威联通 QNAP、Unraid 或 Linux 服务器环境：

1. **进入 Docker 目录**：
   ```bash
   cd media-tools/mediaflow-docker
   ```

2. **准备配置文件**：
   ```bash
   cp .env.example .env
   vim .env
   ```

3. **编排并启动容器**：
   ```bash
   docker compose up -d --build
   ```

4. **检查容器运行状态**：
   ```bash
   docker compose logs -f
   ```
   服务就绪后，访问 `http://<服务器IP>:8080`。后续升级只需在 `mediaflow-docker` 目录执行 `./upgrade.sh`（自动备份 SQLite 数据库、拉取最新代码、重建容器并验证健康状态）。

## ⚙️ 配置指南 (.env)

MediaFlow 所有配置项均以 `MF_` 前缀开头，大小写不敏感：

| 环境变量 | 必填 | 默认值 | 作用与示例说明 |
| :--- | :---: | :---: | :--- |
| `MF_PORT` | 否 | `8080` | Web 界面与 API 服务监听端口 |
| `MF_DEBUG` | 否 | `false` | 是否开启调试模式及详细跟踪日志 |
| `MF_DATA_DIR` | 否 | `./data` | SQLite 数据库、批次快照与执行回执持久化存储目录 |
| `MF_CD2_URL` | **是** | - | CloudDrive2 服务地址，如 `http://localhost:19798` |
| `MF_CD2_TOKEN` | **是** | - | CloudDrive2 认证 Token |
| `MF_MP_URL` | **是** | - | MoviePilot 服务端地址，如 `http://localhost:3001` |
| `MF_MP_TOKEN` | **是** | - | MoviePilot 后台生成的 API Token / Key |
| `MF_SOURCE_ROOT` | **是** | - | 待整理源目录根路径，如 `/115/Library_incs/nas` 或 `Z:\nas` |
| `MF_ARCHIVE_ROOT`| **是** | - | 归档目标根路径，如 `/115/Library_incs/nas.finish` |

## 🛡️ 零数据丢失安全防线

媒体整理最核心的敬畏在于：**宁可暂缓处理，绝不发生误删。** MediaFlow 构建了四层物理级防护锁：

```
┌────────────────────────────────────────────────────────┐
│  第一层：测试与生产强隔离护栏                           │
│  app/database.py 注入运行上下文检测，测试绝不连入生产库   │
├────────────────────────────────────────────────────────┤
│  第二层：CloudDrive2 (1) 后缀与指纹双向校验             │
│  剥离动态序号并校验 (id, size, modified) 防止序号对调误伤 │
├────────────────────────────────────────────────────────┤
│  第三层：纯附件与外层根目录保全事务                      │
│  清源前强制保全 .nfo/海报/外挂字幕，核验到位方可回收源季  │
├────────────────────────────────────────────────────────┤
│  第四层：外部手动删除容错与源目录对账 (v2.5.61)         │
│  强读父目录精确识别物理消失，防范虚假删除，幂等结案      │
└────────────────────────────────────────────────────────┘
```

* **P0 物理防误删探针**：每次执行删除前强制发起实时云盘强读（`force_refresh=True`），只要文件元数据或大小与计划快照不一致，立即中止该项并抛出 `needs_repreview`。
* **隔离测试全矩阵**：工程内包含 167+ 项后端隔离测试套件与 6 份原生前端 DOM/无头脚本，覆盖高并发死锁、断网熔断、幂等回执等全极限场景。

## 💬 常见问题 (FAQ)

<details>
<summary><b>Q1: 为什么执行批量推荐处理时提示需要重新预览 (needs_repreview)？</b></summary>
这是 MediaFlow 核心安全护栏发挥作用的体现。当后台发现自上次生成计划后，云盘中的文件发生了变动（如新下载了文件、网盘外部进行了移动或重命名），系统将主动拦截当前执行以防止误删。此时只需重新点击预览获取最新快照即可。
</details>

<details>
<summary><b>Q2: 115 网盘同名文件的 (1) 后缀会导致重复下载吗？</b></summary>
不会。MediaFlow 在 v2.5.49 中升级了动态指纹模型，通过文件唯一内部 ID、文件大小与修改时间同簇校验，自动识别 CD2 动态附加的 <code>(1)</code> 后缀，既不会误报幽灵文件，也不会误触发重复下载。
</details>

<details>
<summary><b>Q3: 我已经在网盘网页上手动删除了某个目录，为什么列表中还在？</b></summary>
在 v2.5.61 及以上版本中，针对已在外部手动删除的目录，直接进入对应模块点击卡片上的「核对源目录」按钮，系统会强读云盘父目录对账，确认消失后将直接核减条目并更新统计，不再产生报错。
</details>
