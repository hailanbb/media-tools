# 补缺下载：详细需求与业务规则

文档基线：1.4（2026-10-29）。Python 当前核查见 13；历史研究/其他实现核查保留原时点。

关联需求：G-01～G-14、D-01～D-19。依据为上游普通补缺、同版本补缺、播期复核、整理修复要求；本地实现差异见 07，动漫专属补缺见 11。

## 1. 目标与边界

补缺的结果是“哪些资源被明确接收、覆盖哪些缺集、还有哪些未解决”，不是“本季已经齐全”。下载后还要经过下载器、MoviePilot 整理、云端同步和文件复核。

正常补缺与整理修复是两条支路：

    已播缺集
      → 检查真实文件 / 已有下载 / 在途整理 / 未决记录
      → 已有可用文件但整理受阻：检查 → 修复计划 → 执行 → 等待文件核验
      → 确实没有可用文件：搜索 → 选择 → 下载计划 → 提交 → 等待文件核验

不能因为修复检查报错就直接进入普通下载。检查失败意味着事实不清楚，不等于确实没有已下载文件。

## 2. 输入与待补集合（D-01、D-02、D-04）

输入必须有可信剧身份、季号、来源集合、可解释的缺集和排除集合，并确认资源、本地和来源采用相同编号体系或已有有效映射。路径与报告版本有效；保留实际扫描根/profileId，不能随默认根变动重定向；关联操作记录必须完整解析。

在普通单版本模式下：

    本轮可补 = 已确认已播缺集 - 已有活跃任务覆盖 - 未决提交覆盖 - 已验证入库集合

在同版本模式下，已收录与任务覆盖都要附带 versionId。其他版本的 E05 不自动抵扣目标版本的 E05。

| 输入情况 | 行为 |
| --- | --- |
| 来源数量未知或身份冲突 | 暂缓，提示先初检/补查 |
| 缺集为空且已确认 | 不搜索、不下载；有版本异常则转复核 |
| 缺集未知 | 不猜零散集；仅在来源完整、整季证据充分、无已有/未决任务且政策允许时形成整季候选 |
| 缺集全部是待播/日期未知 | 不提交 |
| 绿色或已归档 | 当前核验仍有效且无新增内容时跳过普通补缺；旧别名目录新到文件须重新核对，不能清除未决记录 |
| 只有旧报告且发现混版迹象 | 要求重新扫描文件清单 |
| 已有某季任务但覆盖不明 | 阻挡该季新增提交，先核实范围 |

需区分收藏覆盖与当前目录覆盖。同收藏已核实的关联目录和归档位置可用于避免重复补缺，但必须分别记录所在位置；其他收藏或备份库只作预警，未经身份/范围核验不能抵扣。只读关联有歧义时先核实，不能把未归并的现成文件当作不存在。

### 2.1 初检汇总先于搜索

按来源/媒体类型/ID、收藏范围、逻辑季及编号体系关联多目录与旧标题任务。A/B 文件互补覆盖完整季时普通补缺为空；相同季重复视频转复核；不同季各自核算。即使物理目录未合并，也不能分别为 A、B 重复补齐同一季。

留源未齐全季继续细分：已播真缺进入补缺；在途/待整理先等待或核对；仅未播缺口等待更新；身份、列表、播期未知先待核实。已完成并归档 S01 不终止 S02 的补缺，也不自动订阅或补下未收藏季。

日/韩原名、中文译名、繁简和历史名可作为有出处的补充资源查询词，结果合并去重并再次核实身份与季。中文同名不代表同一作品；新显示名不创建新的防重复任务身份。

## 3. 资源身份与覆盖资格（D-03、D-05）

候选首先通过硬资格检查，然后才能排序。

1. 返回媒体类型是电视剧，ID 与任务一致；明确冲突 ID 直接排除。
2. 无 ID 时使用完整标题/原名、可信别名、年份、唯一候选。标准化不等于模糊匹配授权。
3. 明确单季，季号相等。多季包默认不自动选择，不从包中猜测只下某季。
4. 覆盖集号可靠，不重复、不越界、无多种证据冲突。
5. 有实际可用的下载入口；只在提交时使用，不写进可分享报表。
6. 做种数可确认且至少 2；未知不能按 0 的排序技巧伪装成已知。
7. 至少能补上一集剩余缺集；完全无关的资源，即使做种再多也不选。
8. 搜索不完整要附带状态；不能把请求失败、分页中断解释成“全站无资源”。

整季必须证明其覆盖集合等于可信本季全集，或有一致的明确全 N 集证据。只有 S01、Complete 文案或数组长度相等不足以推翻冲突/越界证据。

## 4. 资源排序的精确定义（D-06、D-07）

本节保留既有下载排序，直至明确选择新的策略。用户已允许按明确偏好自动择版，但不等于采用 Python 当前下载分数、分辨率权重或整季/散集阈值；同版本匹配条件仍算资格，详细偏好见 Q-06。

排序步骤：

1. 在无已有任务重叠的前提下，合格整季优先；没有合格整季再选零散。
2. 同类先看明确中文字幕/配音证据。中文剧名不算；“无中字”等否定证据不能加分。
3. 同等中文条件先选做种 ≥5 的组。
4. ≥5 组容量**全部已知**时，按容量成本升序，再按做种数降序。
5. ≥5 组存在未知容量时，整个组按做种降序；不能把未知当无穷大后声称实现了上游规则。
6. 没有 ≥5 候选时，2～4 做种组按做种数降序。
7. 整季使用总字节；零散使用“总字节 / 本次新补集数”作为比较成本；每次选择后重算。
8. 同分使用稳定资源键作为最后规则，避免接口返回顺序改变结果。

| 候选（其余条件相同） | 应选 |
| --- | --- |
| 中文 2 做种 vs 无中文 100 做种 | 中文 2 做种 |
| 中文 1 做种 vs 无中文 100 做种 | 前者不合格，后者可选 |
| 50 做种 30GB vs 5 做种 10GB | 5 做种 10GB |
| 50 做种 30GB vs 4 做种 10GB | 50 做种 30GB |
| 4 做种 10GB vs 2 做种 1GB | 4 做种 10GB |
| 5 做种 10GB vs 50 做种容量未知 | 50 做种；记录按做种回退 |
| 缺 E02/E04，1.2GB 双集包 vs 各 0.8GB 单集 | 在同一可比较组内优先双集包，成本 0.6GB/新补集 |

已有任务覆盖 E02 时，不选覆盖 E02/E04 的包来再下 E02；只选 E04，或报告暂时没有不重叠资源。包附带已收录本地集与包重叠在途任务应区分：前者在普通整季策略中可能允许，但必须显示额外下载量；后者为防重复阻挡条件。同版本补缺沿用更严格的“不为整季包重新下载已有视频”要求。

选择零散资源是明确的贪心策略，不宣称得到全局最小下载量。若以后改成组合优化，需新增需求与验收，不能静默改变。

## 5. 同版本补缺（D-08）

必须使用与复核相同的版本解析结果及文件快照。

| 版本情况 | 处理 |
| --- | --- |
| 一个完整版本 | 不新增下载，转复核确认是否清理其他版本 |
| 明确允许混版且合格保留集合已完整 | 不为凑单一版本重新下载，转复核按策略确认保留；混版标识保留 |
| 多个完整版本 | 按明确保留偏好形成计划；未配置、并列或证据不足转人工，不按日期单独淘汰 |
| 全部不完整，有资源可补齐其中一个 | 优先能补齐的版本；同等级按可信云盘修改时间 |
| 只能部分补齐某版本 | 保持该版本目标，记录剩余，不自动混入不同发布组 |
| 时间相同/未知、版本标记不足 | 交人工，不猜最优版本 |
| 混版且已有本季下载或提交记录 | 先让既有任务闭环并复核，防止不同版本抵扣同一集 |

同版本资格核对发布组及已有证据中的分辨率、来源、编码、音频、HDR 等。没有相关标记是未知，不自动解释为一致。文件已被重命名丢失标记时，不能以同标题恢复发布组。

## 6. 防重复与提交状态（D-09～D-12）

防重复依据应同时覆盖：

- 本地持久记录：准备、提交中、接受、未知、已核验等。
- 导入报告：其他运行或设备留下的记录。
- MoviePilot 当前下载任务：包括搜索期间新出现的任务。
- 整理队列与历史：已经下载但尚未写入源库。
- 新鲜文件快照：确实已经进入正确目录的文件。

建议状态：

    planned → submitting → accepted → downloading → transfer-pending → files-verified
                            ↘ rejected
                 ↘ uncertain → reconcile → accepted / proven-not-submitted / manual

关键约束：

1. 在请求前原子保存 submitting；保存失败不提交。
2. 远端明确成功且有稳定任务标识才是 accepted；无任务 ID 进入 uncertain。
3. 请求超时不等于失败。下次运行先查询，不自动再下。
4. 活跃任务消失不等于取消：也可能下载完、转移中或服务清理历史。必须结合其他证据。
5. 人工解除防重复应记录原因和核实证据；不能靠记录到期自动重新提交。
6. 普通下载使用 MoviePilot 现有下载器与保存设置，不修改全局设置。
7. 单季分成多项提交时逐项保存，部分成功只阻挡已覆盖/未知范围，不能丢失剩余集目。

去重键建议由稳定媒体/季/版本/资源身份构成；不能只用正规化剧名。记录包含 resourceKey 而不保存私密下载 URL。

## 7. 整理修复（D-15～D-17）

这是会删除整理历史并提交复制的独立写能力，不能隐藏在普通“搜索”或“检查”里。

### 7.1 只读检查的前置条件

- 用户已确认服务为 v2.15.6；实际接入仍需验证能力与响应。公开文档 v3.1.9 只用于升级参考，不凭猜测混用接口。
- 本剧本季身份明确，缺集已确认，文件清单足够新且没有混版歧义。
- 全部分页整理历史读取完成，目标集对应唯一明确历史 ID。
- 已下载完成，无活跃下载/整理仍在修改源文件；源文件存在、大小可信、存储身份明确。
- MoviePilot 下载路径、整理目标路径与 CloudDrive2 展示路径存在已验证映射。
- 预览中每个对象的剧、季、集、源、目标、存储、操作类型都精确匹配；不能只看 summary.failed 为 0。
- 原记录若处于未知状态，优先只读 reconcile，不生成另一份可执行计划。

### 7.2 计划和执行

计划列出每集的历史 ID、必要历史快照、源文件属性、预计目标、复制参数和风险。审批绑定计划版本，不直接执行报告中携带的请求体。

执行前必须依据官方 v2.15.6 ManualTransferItem 构造请求；本地现有嵌套 media_info/meta_info、overwrite_mode 不能替代契约核对，也不能仅凭请求字符串证明服务不覆盖，见 10 第 5.3 节。

执行顺序：

1. 重新核验源文件、历史与预览，确认计划未变。
2. 保存 history-delete-pending。
3. 仅删除指定历史；deletesrc=false、deletedest=false；核实历史删除结果。
4. 保存 transfer-pending。
5. 提交单集复制、禁止覆盖；记录明确响应或 uncertain。
6. 等实际目标文件核验，不以提交成功解除清理/归档阻挡。

不得调用全局重整、按 logid 扩大重整、reorganize、删除视频或覆盖目标。未支持的接口形态必须停在计划阶段。

### 7.3 部分修复

缺 E02/E04，仅 E02 有历史时，E02 修复与 E04 待下载分开记录。E02 未决不能清季、不能归档。是否同轮继续对 E04 下载取决于能否证明没有交叉影响；默认先形成可审阅的独立计划，不让异常处理自动落入下载。

修复记录损坏或出现不支持版本属于阻挡，不等于“没有修复记录”。

## 8. 搜索差异与报告（D-13、D-14、D-18）

登记 100 集、资源站最高 E42，只能说明本轮见到的覆盖范围。需记录覆盖集合，不能推断 E01～E42 全都有，也不能把总数改成 42。

只有可信同剧同季的播期证据才改连载状态。已提交/已有任务时，黄色保持复核入口，播出事实另列；不为改变颜色而额外进行无必要搜索。

每个资源记录：媒体/季/版本、站点、标题、资源类型、覆盖与本次新补集合、剩余集合、做种快照及时间、容量、中文证据、选择依据、任务 ID、请求状态、响应和核实时间。数量未知用 null/未记录，不填 0。

对应验收：T-D01～T-D16、T-F01～T-F09，以及 T-P 中版本/请求契约与 T-N 中动漫候选覆盖场景。动漫细节集中见 [独立动漫专项](11-动漫整理专项需求与命名规范.md)。

## 9. 1.4 新增选择与状态要求

资源完整覆盖、本轮新补覆盖、本地已有覆盖和在途重叠分别记录。每次候选选择、实际提交前重算；整季资格使用可信集合，不以列表长度或仅 S01/Complete 标记推定。活跃任务集数字段空是未知，查询失败不当空列表；30 分钟等有效期只能触发重新核实，不能自动解除未决。

明确频控与本轮限额，保留未处理集和续办状态；限制耗尽、无源、拒绝、提交未知分别展示。已接收需稳定标识、事前记录与事后核验；多资源部分失败不把所有未覆盖集统一称无源。

新版 Python 已有缺集交集过滤、多候选及队列读取，但存在整季覆盖、防重时点、超时记录与硬编码策略差异。具体权重、<=3 集/<35%、15 项/0.5 秒仅为当前实现事实，非已确认通用默认。体积/集数不等于实际码率，不作内容质量证明。详见 [13 专项](13-Python版更新核查与需求补充.md) P-01～P-05、Y-01～Y-04。
