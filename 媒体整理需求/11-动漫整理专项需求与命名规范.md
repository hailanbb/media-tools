# 动漫整理：专项需求、Emby 命名与阶段差异

文档基线：1.4（2026-10-29）。Python 当前核查见 13；历史研究/其他实现核查保留原时点。

原专项研究日期：2026-10-27 · 研究基线：1.2；当前需求修订为 1.4

**本文件独立维护动漫整理内容。** 用户已确认动漫主要使用 S01E01 季集编号；初检范围要增加动漫，并支持自定义修改根目录。正文中“建议”描述后续设计，不表示已改动源文件或媒体库。

本次没有操作 Emby，也没有修改文件名、MoviePilot 设置或任何实际库路径。绝对集号、电影、特殊篇等边界会识别并解释；不要求用户先重命名整个动漫库。

## 1. 研究结论与事实边界

Emby 的官方 TV 命名文档给出“剧目录/季目录/季集文件”的结构，也允许 TV 库下剧根直接放季集文件；季 0 使用 Season 0、Season 00 或 Specials。支持同季多集文件及多版本，也定义了 extras 等附加内容。**动漫是内容类别，不因此产生一套可忽略媒体类型和季集身份的通用规则。** 本文以季集式为用户当前基准。[Emby TV 命名](https://emby.media/support/articles/TV-Naming.html)

动画电影按电影对象识别；电影文档采用作品名、年份及独立作品目录，不能把电影文件强加 S01E01。[Emby 电影命名](https://emby.media/support/articles/Movie-Naming.html)

Emby 团队曾明确说明 TVDB 绝对编号需对应绝对顺序及文件编号；这是 2019 年官方团队回复，仅用于证明“编号与来源顺序需一致”，不作为当前所有插件/版本的兼容保证。[官方团队回复](https://emby.media/community/topic/75674-absolute-series-scanner-anime/)

特殊篇也可能包含用户自编号内容，不能把所有 S00 集号都视为来源登记的正片或缺集目标。[Emby 特殊篇顺序说明](https://emby.media/support/articles/Ordering-TV-Specials.html)

**工作流可安全自动处理的范围，需要额外的来源、映射、版本和文件核验；Emby 能展示某种命名，不代表本项目当前已经支持相同操作。** 下文是结合这些事实制定的项目需求与设计。

## 2. 与普通电视剧的共同点和差异

| 维度 | 可共享部分 | 动漫需要增加的处理 |
| --- | --- | --- |
| 媒体身份 | ID、类型、名称、年份 | 同名续作/前传/重制/剧场版必须分开；Part 2 不自动等于 Season 2 |
| 编号 | SxxExx、可信本季集合 | 分割季度、来源剧集组、偶发绝对集号，先确定对应关系 |
| 特殊内容 | 额外视频保留 | OVA/OAD、SP、总集篇、预告、NCOP/NCED 等需辨别角色，不能都算正片 |
| 版本 | 完整版本与不完整版本 | TV/BD、修订 v2、字幕组、双音轨、画面修正可能是有意并存 |
| 文件形态 | 单集文件与配套 | 合并集、多段单集、外置字幕/字体/章节、原盘与链接类文件 |
| 完结 | 本季证据判断 | 分割季度间休播不能因最后一集日期过去就判整部永久完结 |
| 归档 | 全清单、目标保护 | 动画电影单列；特殊篇/附件不能被根目录清理吞掉 |

“TV/BD”“字幕组”等是版本区别证据，不新增“某组更好”“BD 一定优先”规则。用户并未指定这些偏好。

## 3. 命名建议：检查与展示，不自动改名

以下虚构例子是项目推荐展示形式，不是必须覆盖现有命名的指令。

### 3.1 季集式动画

    <动漫扫描根>/
      <可选分类>/
        示例动画 (2024) [tmdbid=示例ID]/
          Season 1/
            示例动画 - S01E01 - 开篇.mkv
            示例动画 - S01E02 - 继续.mkv
          Season 0/
            示例动画 - S00E01 - 特殊篇.mkv

文件名中的 ID 占位符仅用于说明，实际应填写可信数字 ID。推荐 S01E01 作为统一交流形式；其他可识别格式只读兼容，不能因不符合推荐形式就删除。

### 3.2 合并集与版本

    示例动画 - S01E01-E02 - 合并篇.mkv
    示例动画 - S01E01 - TV版.mkv
    示例动画 - S01E01 - BD版.mkv

合并集是一个物理文件覆盖多个逻辑集；多版本是不同文件表达同一逻辑集。两者统计、补缺、清理完全不同，不用单个 episode 数字表示。

### 3.3 动画电影

    <电影扫描范围>/
      示例动画电影 (2025) [tmdbid=示例电影ID]/
        示例动画电影 (2025).mkv

如果动画电影混在动漫根，初检应列出 mediaKind=movie 并从逐季补缺流程隔离。是否另建电影整理流程仍待讨论；不把“支持动漫初检”推定为已经授权电影自动下载/归档。

### 3.4 不确定内容

    [字幕组] 示例动画 - 013 [1080p][校验码].mkv
    示例动画 - 12.5 - 总集篇.mkv
    示例动画 - S01E01 - part1.mkv
    示例动画 - S01E01 - part2.mkv
    NCOP01.mkv
    NCED01.mkv

013 可能是本季集号也可能是全剧绝对集号；12.5 不能截为 12；part1/part2 不能按同集重复副本删一半；OP/ED 不是 E01 正片。这些名称只是分类线索，必须结合路径/来源核实。

## 4. 自定义根目录与扫描范围

关联需求 I-14、G-01、G-08。此需求适用于电视剧和动漫，不是只给动漫增加一个硬编码路径。

### 4.1 用户操作需求

1. 可查看、修改并选择初检根；支持“仅本轮使用”和明确保存默认值，不能输入一次就悄悄改所有后台任务。
2. 可分别选择电视剧与动漫范围，或选择二者；报告必须显示实际包含的根/分类/作品。
3. 明确目录布局：根下是分类、根下直接是作品、当前路径是单作品，或自动检测后需要确认。
4. 选择根后先只读列举并提示范围；配置根不可达时保留错误，不退回旧默认根或全盘。
5. 支持一个内容类多个根作为建议扩展；不能由于 Emby 合并展示多个路径，就合并为一个可互相删除的物理目录。

Emby 媒体库本身可包含多个物理路径；**本工作流的扫描根**和**Emby 挂载/展示根**应分别记录，不能推定二者字符串一致。[Emby Library Setup](https://emby.media/support/articles/Library-Setup.html)

### 4.2 路径配置设计示意

以下仅是未来 schema 示例，不是可以直接替换当前 config.json 的已实现配置：

    {
      "libraryProfiles": [
        {
          "profileId": "tv-main",
          "contentKind": "tv-series",
          "sourceRoot": "/example/电视剧",
          "layout": "category-series-season",
          "archiveRoot": "/example-finished/电视剧"
        },
        {
          "profileId": "anime-main",
          "contentKind": "anime-series",
          "sourceRoot": "/example/动漫",
          "layout": "series-season",
          "archiveRoot": null,
          "numberingDefault": "season-episode"
        }
      ]
    }

archiveRoot=null 表示仅检查/待指定归档映射；不影响只读初检。下载路径和整理目标需要各自的 MP 存储映射，不能照抄扫描路径。

### 4.3 根变更必须贯穿下游

- 报告保存 profileId、实际 sourceRoot、showPath、seasonPath、scopeId、configRevision。
- 下阶段读旧报告不得使用“当前 sourceRoot + 分类 + 剧名”重新拼出新路径。
- 修改默认根后，旧 runId/操作日志仍绑定原根；明确迁移关系前不改写旧历史。
- 临时扫描根在常用库外时可以形成明确只读 scope，但清理/归档需要另行核实写范围与目标映射。
- 根包含关系、相同存储重叠路径应去重或阻挡；禁止把目标归档根又扫描为待清理源。
- 不同根同名/同 ID 动漫保留不同 collectionId，不能用名称去重误删有意副本。

当前本地已有 paths.source 与 inspect --path 的基础，缺口在统一配置体验、报告真实路径持久化及下阶段范围衔接；不能描述成“完全不能改根”。

## 5. 媒体、季、分部与编号

### 5.1 四个身份维度必须分开

    contentKind: anime-series / tv-series / anime-movie / unknown
    mediaIdentity: provider + nativeId + mediaType
    numberingScheme: season-episode / absolute / episode-group / custom / unknown
    collectionIdentity: libraryProfile + realPath

“动漫”是内容分类，MP 的媒体类型仍可能是“电视剧”或“电影”；不能在接口里凭空发送 media_type=动漫。日本产地也不等于动漫，中文目录名也不是唯一分类证据。

### 5.2 用户当前基准

S01E01 为主要模式；对明确同一来源季的普通动画，复用电视剧集号和完整性计算。需要增加下列差异诊断：

| 场景 | 规则 |
| --- | --- |
| 标题有 第二部 / Part 2 / 后半，但文件仍为 S01E13 | 不强改 S02；查来源是否同季分割播出 |
| TMDB 将续作归为同剧 S02，豆瓣分为独立条目 | 显式保存“TMDB 剧+S02 ↔ 豆瓣续作条目”绑定 |
| Emby 选 TVDB/剧集组顺序，MP 以 TMDB 默认季编号整理 | 标 order-mismatch；先映射，不能直接计算缺集 |
| 短篇/总集篇被来源纳入正片或 S00 | 以明确条目为准，不仅凭名称排除 |
| 用户文件为绝对 25，来源为 S02E01 | 有经过验证映射才换算；不按上一季 24 集盲减 |
| 一个文件跨两季 | 不归入普通同季合并集，保持人工核实 |

映射至少保存原始编号、目标季集集合、来源/组 ID、规则版本、证据与是否人工确认。映射变化使依赖的缺集、下载计划、清理计划失效，重新计算。

### 5.3 与豆瓣触发规则的结合

必须先映射再比较：

    文件原始编号 → 确认媒体/季/编号体系 → 归一到本季集合
      → 与 TMDB 同体系集合比较
      → 真正超出范围时，经 MoviePilot 查询豆瓣

未解决的 order-mismatch 不是“TMDB 登记少了”。豆瓣总数更大也不能直接证明映射正确。通道、字段可信度和 v2.15.6 季号推导限制见 [MoviePilot 接入方案](10-MoviePilot接口研究与接入方案.md)。

## 6. 季 0、OVA/OAD 与附加内容

建议先分类，再统计：

| 角色 | 识别依据 | 是否计入正片缺集 |
| --- | --- | --- |
| 正片 episode | 同季来源集目与文件证据 | 是 |
| 来源登记特殊篇 special | 来源特殊季/条目 + S00 映射 | 单独统计，不塞进 S01 |
| 独立动画电影 movie | 电影身份 | 否，另列 |
| OP/ED/PV/CM/花絮 extra | 明确角色/路径与命名证据 | 否；保留，不视为多余视频自动删除 |
| 用户自编号 special | 显式人工映射 | 按用户集合，不补来源不存在的“空洞” |
| 角色不明 unknown | 证据不足 | 不猜；相关写操作阻挡 |

不能规定 OVA 一律放 Season 0：不同来源可能是独立剧、电影或特殊季。Season 0 通常需要显式收藏集合而非“从 1 到最大集号全都要收齐”的规则，否则会产生大量错误缺集。

初检应记录特殊篇和附加内容，即使尚未支持它们自动补缺。整剧归档时不能因为正片完整，就递归删除未审阅的特殊篇/附件。

## 7. 四阶段如何处理动漫

### 7.1 初检

- 记录 contentKind、编号政策、真实根/作品路径，保存分类来源。
- 正片/特殊篇/附加视频/电影/未知分别计数；不把扩展名属于视频的所有文件都映射到正片集合。
- 普通季集式继续按本季来源核验；分部与顺序冲突优先解决。
- 对 Emby 合法的剧根平铺文件可形成逻辑季视图；没有物理季目录不等于没有任何集号。当前实现未支持时明确列 layout-unsupported，而非猜 S01。
- 对合并集保留 coveredEpisodes[] 与 fileId；对多段单集保留 segment 关系和完整性未知。
- 再应用 TMDB 超范围 → MP 豆瓣复核规则；已有完整版本不必重新下载。

### 7.2 补缺下载

- 候选必须匹配同一动画作品、季/分部与编号体系。
- 简繁、日文、罗马字、别名仅用于候选识别，不能用主标题模糊相似代替身份。
- 同版本补缺保留字幕组、发布组、TV/BD、修订标记等证据。v2 是修订线索，不是必然更好；不同文件 hash/CRC 字样也不是自动去重证明。
- 已有 E01-E02 合并文件时，不能再下 E01/E02；无法确认完整覆盖时先核实。
- 动画电影不进入本季下载；OVA 归属明确后才能决定适用支路。
- 不新增默认画质、大小、音轨、字幕组偏好；仍用已确认资源排序。

### 7.3 复核清理

- “一逻辑集一个文件”不再是普遍规则。单文件多集、多文件单集和多版本各自有关系模型。
- 删除前验证保留文件集合覆盖全部需保留逻辑集；不能删一个合并文件只因为其中一集有重复。
- TV 与 BD、修订版、不同字幕组并存时，1.4 允许按明确偏好自动择版；未配置、并列或覆盖/字幕等证据不足仍交人工。不能把 v2、较大或较新本身当质量证明。
- 1.4 允许清理经核实仅属淘汰视频的外置字幕；保留版需要或共享字幕、配对不全/未知字幕、字体 .ttf/.otf、章节和其他未知附件继续保留，不从“不是视频”推定可删。
- OP/ED/PV 等作为受保护附加内容，不按同名或 E01 数字片段并入冗余正片。
- 合并集/分段的自动删除尚未验证时，只读分析、列原因，禁止套用单集删除算法。

### 7.4 归档

- 作品内所有物理对象都进清单，逻辑季与物理目录分别记录。
- 正片全绿仍需核对未知附加目录、未决映射、来源特殊篇或动画电影的归属；明确独立保留项不必阻挡其他完成季，可能影响所选季的未知项仍阻挡。
- 目标同季逐文件核对互补、重复与配套，只有明确计划可合入；不得为了适配动漫自动重编号、合并 Part 或创建隐式别名。
- 已核实附加内容可以作为受保护迁移单元进入计划；未实现此能力时暂缓，不能移完季后直接删根。
- 1.3 支持所选完成季先归档，其他未齐全季/S00/extras 可明确留源；先核对内容归属与共享依赖。跨季文件、无法独立保留的资料或未知映射会阻挡相关计划，不直接整体搬走剧根。

## 8. 文件与逻辑集关系设计

建议保留如下结构，而不是只保存 episode=数字：

    fileId: physical-file-001
    role: episode
    nativeEpisodeLabel: S01E01-E02
    canonicalEpisodes: [S01E01, S01E02]
    coverageKind: multi-episode
    mappingId: mapping-001
    versionId: version-a
    protectedAttachments: [attachment-001]

分段单集还需 partIndex、expectedParts（未知时 null）和 segmentStatus。绝对集号映射还需原始序号及对应证据。不能用数组长度来猜合并片是否真的覆盖内容；文件名证据与媒体内容核验等级仍分开。

此模型可先用于报告，只有通过相应用例后再放开自动下载/清理/归档。建议分级：

- A：普通 SxxExx、明确季/身份，可进入既有规则链。
- B：明确特殊篇、extras、同季合并集，先完整分析与保护，按能力放行。
- C：绝对/自定义/分段/跨来源多义，先映射或人工。

## 9. 独立动漫报告需要展示什么

每部/季记录：实际根、作品路径、contentKind、媒体 ID、来源季与物理季、编号体系、剧集组 ID、映射依据、正片/特殊/附加视频数、逻辑集集合、合并/分段关系、超范围、缺集、版本、豆瓣触发原因和 MP 查询状态。

未知电影/OVA/附加目录也要在异常或清单中出现，不因“不属于普通季”而消失。主报告可按类别筛选，动漫专项页可解释差异；不复制一套独立业务状态以免与电视剧流程分叉。

## 10. 待讨论与当前处理

用户已确认：主要 S01E01、初检加入动漫、根可自定义、豆瓣经 MP、MP 为 v2.15.6；这些不用重新询问。

仍未确认：

| 事项 | 当前文档处理 |
| --- | --- |
| 是否补全来源登记的全部 S00 | 只记录，不默认全补；需明确收藏范围 |
| 绝对集号/自定义映射来源 | 保留解析与映射待办，不猜偏移 |
| 剧场版是否开展完整电影整理 | 初检分类识别，排除季流程，后续单独决定 |
| 动漫多完整版本/混版的具体偏好 | 用户已允许按明确偏好自动择版；独立收藏仍隔离，偏好未配置或证据不足转人工 |
| Emby 实际元数据提供方、排序和插件 | 未获取，不宣称与现有配置完全一致；只在发现具体冲突时索取必要信息 |
| 归档目标根和 MP 存储映射 | 初检可以先做；写阶段缺映射则阻挡 |

对应需求：I-14～I-18、D-19、R-13、A-13；对应验收：T-I13～T-I15、T-N01～T-N12。基础规则仍见 01，来源接入见 10。

## 11. 多语言同剧、多目录各季与留源（1.3）

动漫目录的日文/韩文/罗马字、繁体中文与简体中文名称，优先通过可信来源身份和译名关系对应。简体显示名可以辅助查找已有中文目录；无中文译名时保留原名并待确认，不把机器翻译当成官方名称。原名、语言、来源与原始路径始终保留；自动重命名不属于初检。

同一收藏可能 A 有 S01/S02、B 有 S01/S03。逐季汇总，只有编号/分部/剧集组一致才聚合；不同季不互相抵扣。Part 2 不自动等于 S02，S00 与独立 OVA/电影身份仍需核实。跨目录同集重复、TV/BD、修订版、上下段和合并集按原有版本/覆盖规则处理。

完成且可安全分离的 S01 可先归档；未齐全或连载 S02 留源，按已播缺集/在途/待播/未知分别处理。根 NFO、共享字体、字幕包及特殊内容保护；不能因为已移动 S01 就删除剧根。共用规则及案例集中见 [12 专项](12-同剧多目录与分季归档专项需求.md)，动漫特有差异继续在本篇单独维护。

## 12. 1.4 Python 策略变化对动漫的限制

不能将长剧每集体积阈值硬套短篇动漫，体积不是码率/画质测量。发布组一致性属于线索，TV/BD、修订、音轨/字幕差异仍须核实；合并集、多段单集使用覆盖关系，不能按文件数判季齐全或漏移。

自动择版须明确是否允许混版、需要的语言/强制字幕/特效，以及目标版本条件；字幕清理必须证明保留版本不依赖该字幕。字体、特效附件、NCOP/NCED 等不因允许字幕清理而扩大删除。动漫多语言身份与跨目录聚合仍按 11/12 专题目标处理，不能从归档后新增 ID 提取函数推断已整体实现。对应 Y-01、Y-05～Y-09，见 [13 更新核查](13-Python版更新核查与需求补充.md)。
