## 文档中的四种结论

- **继承**：在所审阅的上游需求中有明确依据；不等于已由 Windows 版实现。
- **修正**：根据代码、上游规则或可复现结果，纠正矛盾、遗漏或错误。需要修改源码时，仅列待办。
- **建议**：本次提出的实现或产品增强方向，尚未当作用户已确认的业务偏好。
- **待讨论**：缺少事实或存在业务取舍，先保留问题与选项，不编造结论。

功能需求使用 G、I、D、R、A、X 编号；验收使用 T 编号；实现差异使用 F 编号。修改某条规则时，应同时更新详细需求、对应测试与变更记录。

## 1.3 的核心规则

1. 初检先将日/韩/繁体名称对应到可信中文显示名与作品身份，查找同剧目录；同中文名不能直接合并，原路径不改写。
2. 多目录的相同季聚合、不同季独立核算；分散内容已覆盖时不盲目补缺，重复与混版转复核。
3. 集号覆盖、目标版本完整、本季播完和可归档分别判断。文件数量够不代表完整。
4. 已完成季可先归档；未齐全季留源，按已播真缺、待整理/在途、待播和未知分别处理。保护留源季和根共用资料，不能误报整剧完成。
5. 副本不按修改时间单独淘汰，主目录不随显示名动态变化。豆瓣经 MP v2.15.6 的既有规则保持；后台长期自动写入仍待讨论。

本版共 99 条需求、135 个验收场景。它们是目标标准，不能视为代码已实现或生产环境已经验证。07/09 的旧实现核查为历史材料，本轮未追加代码审阅结论。
