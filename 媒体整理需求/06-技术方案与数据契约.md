# 技术方案与数据契约

文档基线：1.3（2026-10-27）。本轮只更新需求；历史研究/实现核查保留原时点。

本章是满足需求的**建议实现方案**，不是已经存在的接口或源码。本次不创建这些模块、不变更配置、不安装依赖。业务规则以 01～05 为准。

## 1. 架构取舍

建议保留现有 Node.js CLI、四阶段组织和 CD2/MP/TMDB 客户端边界，优先补齐共用规则与状态层，不为单机个人工作流立即引入 Web 服务、消息队列或微服务。

当前模块与建议职责：

| 层 | 现有基础 | 建议职责 |
| --- | --- | --- |
| 入口 | bin/tv-workflow.js、bin/tray.js | 解析动作与范围、选择 runId/planId、显示计划、返回真实退出状态 |
| 编排 | lib/stages/index.js | 按状态推进、暂停/恢复、依赖与阻挡检查、执行锁 |
| 领域规则 | lib/core | 身份、集号、来源、版本、补缺选择、清理/归档计划；尽量纯函数 |
| 外部适配 | lib/clients | 协议、认证引用、分页、超时、错误分类、能力声明；不自行决定业务可否删除 |
| 存储 | lib/platform/data-store.js | 操作意图、快照、计划、状态、事件、恢复与锁 |
| 报告 | lib/core/report-adapter.js | 新旧格式转换、人工字段保留、明细导出；不能成为唯一运行状态库 |

建议演进为：

    输入/CLI → 校验范围和权限 → 读取事实 → 纯规则生成计划
                                               ↓
                               计划审阅 → 持久化 → 执行器
                                               ↓
                                      只读核验 → 更新状态
                                               ↓
                                        报告与摘要

这样浏览器版和 Windows 版可以复用规则测试，平台特有逻辑只在适配器中变化。

## 2. 核心数据模型

### 2.1 稳定身份

建议分离以下标识：

| 标识 | 用途 |
| --- | --- |
| libraryId | 某个服务实例、存储及根范围，不使用 token 作为身份 |
| profileId / configRevision | 用户选择的电视剧/动漫扫描配置与版本；根变更不能改写旧运行身份 |
| mediaId | provider + mediaType + 来源原生 ID；显示名不参与身份；无可信 ID 时显式临时身份，禁止自动写 |
| seasonId | mediaId + 分季体系 + 季号 |
| collectionId | 明确媒体库、存储/根和收藏目的的一套收藏，可关联多个物理目录；独立质量/语言/备份收藏分开 |
| recordId | 季记录稳定 ID，不采用 Excel 行号 |
| runId | 一轮检查/处理，记录输入范围和开始/结束状态 |
| snapshotId | 一份完整文件/来源快照 |
| planId | 绑定规则版本、来源与文件快照的具体计划 |
| operationId | 一个不可混淆的外部写操作 |
| resourceKey | 资源的稳定非秘密身份，用于防重复 |

不建议直接把正规化剧名拼进数据文件名：非法字符替换、截断和跨分类重名会发生碰撞。可用规范结构序列化后哈希，原字段存在记录内部供审阅。

### 2.3 文件清单

每个条目至少包含：

    originalPath, relativePath, name, type, sizeBytes|null,
    modifiedRaw|null, modifiedAt|null, fileId|null,
    parseStatus, season|null, episodes[], versionId|null,
    observedAt, sourceAdapter, attributeCapabilities

动漫与特殊布局增加 fileRole、nativeEpisodeLabel、canonicalEpisodes[]、coverageKind、mappingId 和分段关系；不要把一个文件固定等于一集。mappingId 关联提供方、剧集组、原编号与规范季集，改变映射须使相关计划失效。完整关系模型集中见 [动漫专项](11-动漫整理专项需求与命名规范.md)。

注意事项：

- sizeBytes 未知用 null；0 表示确认零字节。超过 JavaScript 安全整数范围时使用十进制字符串，并在契约中声明。
- 原路径保留原字节/Unicode 语义；比较键可以正规化，但不能覆盖原值。
- 集合去重且稳定排序；遇到非法值直接验证失败，不静默丢弃。
- 快照哈希应按稳定排序与结构生成，排除 observedAt 之类每次变化的字段。
- 时间及其可信性单独记录；修改时间不用于单独判定副本保留优劣，遵循 R-06。

### 2.4 来源证据

记录 provider、URL/引用、查询时点、有效期、媒体身份、季号、集目、日期、结束/季终依据、原始诊断及来源选择政策版本。

经 MoviePilot 取得豆瓣时另存 accessedVia、adapterVersion、subjectId、bindingId、count、episodeEvidenceKind、seasonEvidenceKind。没有 MP 暴露的原始抓取时间就记 null；MP 从总数合成 1..N 时标 count-derived，不能标为已获得逐集日期。

一个来源失败不会删除另一个来源的有效结果。缓存必须以媒体/季/分季体系为键，包含获取时间和失败状态。过期不是自动失效为 0；应保留旧证据并说明不够新，按动作风险决定是否需要刷新。

有效期、刷新频率没有本次已确认数值。建议按播出中/已完结和来源变化风险配置，不把上游网页缓存期限直接当作 API 保证。

### 2.5 多语言、多目录与按季归档记录（1.3）

以下是数据需求，不规定新增程序模块：

| 记录 | 必要信息 |
| --- | --- |
| 名称关系 | 原始目录名、原名、简体中文显示名、译名/别名、来源语言/地区、对应身份与核实依据；无译名明确未知 |
| 收藏及目录成员 | 同收藏关联的物理目录、源/归档/独立备份角色、真实路径、范围与关系依据；名称变化不换收藏身份 |
| 目录与季矩阵 | 每目录实际季、逻辑季/编号映射、集覆盖及版本、重复/未知；不能只存一个 showPath |
| 聚合判断 | 文件数、不同集号数、普通已播缺集、目标版本缺集、在途/待整理覆盖、归并可行性、扫描完整性 |
| 主目录 | 分别记录源和归档角色、确认依据、历史路径及变更；不因显示名更新重拼 |
| 归档计划 | 按季/整剧模式、所选季、迁移单元、目标已有清单、预期留源清单、附件依赖、必要复制、收尾条件 |
| 归档结果 | 季成功/本轮完成/收藏部分归档分开；已归档季新到内容和剩余季状态继续追踪 |

原始物理目录实例与 collectionId 分开保存；一个收藏可有多个目录，一个逻辑季也可有多个实际季目录。旧记录按路径生成的收藏键不得无依据重新归并；先建立可追溯关系再迁移旧记录。

中文同名、繁简转换和机器翻译不作为唯一键。来源集目和文件快照变化要重评估计划；名称显示更新不自行修改既定目标。并发边界覆盖所选季与共同依赖，外部工具仍需核对/协调。

旧报告无 archiveMode/selectedSeasons/retainedInventory 等语义信息时，只读导入并补齐范围，不能按新版默认值直接移动。物理字段可采用适配器命名，但含义必须完整。

## 3. 状态机与阶段衔接

### 3.1 业务状态与操作状态分离

业务事实：身份已核实、缺哪些集、版本是否完整、播完是否成立。

操作事实：下载是否提交、修复是否未决、删除哪一项成功、移动哪一季完成。

展示颜色：这些事实的视图，不是实际执行权限。建议：

| 展示 | 条件 |
| --- | --- |
| 紫 | 对应逻辑季及其计划归档已核验成功；不表示其他季也完成 |
| 黄 | 存在已提交任务或需复核/清理的事项 |
| 绿 | 满足完整、播完、无异常及无未决操作，可进入归档预检 |
| 蓝 | 有本季连载证据，且无更高优先的待复核任务 |
| 红 | 搜索已完成但无合格资源 |
| 无填色 | 来源/身份/结构/播期未知或一般待处理；同时显示具体原因 |

颜色与事实冲突时保留人工修改记录并阻挡写操作，不能自动“信绿色”。

### 3.2 运行状态

    created → inspecting → planning → awaiting-approval → executing → verifying
                    ↘ blocked          ↘ paused            ↘ uncertain
                                                              ↓
                                                           reconcile
                                                              ↓
                                                    verified / partial / failed

长时间下载必须是等待状态，不能“下载提交后立即串行跑完其余阶段”来实现全自动。未来 auto 应：

1. 处理已就绪对象。
2. 持久化等待下载/整理/云端同步的对象。
3. 结束本轮并返回真实摘要。
4. 下次被用户或已授权调度触发时再检查就绪条件。

不要用无限等待阻塞整库，也不要因某一季失败阻塞完全独立的其他剧。共享服务鉴权失败、库根错误、锁损坏则属于全局阻挡。

### 3.3 操作记录

Operation 至少包含：

    operationId, planId, taskId, action, state,
    sourceSnapshotId, targetSnapshotId, requestDigest,
    sourcePath, targetPath, expectedPostcondition,
    preparedAt, submittedAt, respondedAt, verifiedAt,
    remoteTaskId, attempt, errorCode, evidenceRefs

action 可为 submit-download、delete-history、copy-transfer、delete-file、move-unit、delete-empty-directory。每个动作记录自己的批准范围，不能用一次“运行流程”无界覆盖所有未来动作。

请求摘要使用白名单字段，不能保存 Authorization、api_key 或私密下载 URL。回读报告中的请求数据只作证据，执行时重新生成合法请求。

## 4. 持久化、并发与崩溃恢复

当前 JSON 临时文件替换可以作为起点，但需要补充：

1. schema 验证；记录不存在、损坏、权限失败分别返回。
2. 唯一临时文件名、原子替换、必要的落盘保证；写意图失败时不发外部请求。
3. 单进程执行锁 + 跨进程库/季/剧锁，防止 CLI、控制台和定时器同时写同一对象。
4. 操作日志与最新状态关联，不能只在整个阶段末尾写 Excel。
5. 启动时扫描 pending/uncertain，先恢复核验，再接受同对象新计划。
6. 锁所有者、进程/实例标识和心跳；过期锁不直接证明原请求没生效。
7. 报告导出失败不抹掉已经执行的操作；允许从状态库重新导出。

小规模单实例可继续使用 JSON + 操作日志；当跨进程并发、查询与迁移复杂后再评估 SQLite。选择数据库属于实现决策，不能代替正确的远端请求语义。无论哪种存储，都不能承诺跨本地数据库和外部云服务的原子事务。

启动恢复流程：

    读取未决记录 → 验证结构/完整性 → 查询远端任务或源目标现状
      → 已生效且后置条件满足：补记 verified
      → 明确未提交：保留可重新规划资格
      → 仍在途/事实不足：保持 uncertain
      → 冲突/数据缺失：人工处理

## 5. 外部适配器与真实版本核验

### 5.1 CloudDrive2

本地当前实际使用轻量 Protobuf 与 gRPC-Web，并非 README 所说的普通 REST 文件 API。方案须以服务协议和实测版本为依据。

需逐项确认：

- GetSubFiles 流/分页是否完整，错误尾帧与截断帧如何识别。
- 文件类型、大小、ID、修改时间字段的协议定义。
- FindFileByPath 明确未找到与权限/网络失败的区别。
- MoveFile 冲突策略枚举与默认值，是否支持真正拒绝覆盖。
- 跨云移动的复制/删除行为与任务状态。
- DeleteFile 是软删除还是永久删除，实际存储后端的回收能力。
- 返回成功与底层云端可见之间的延迟，以及强制刷新作用。

适配器输出建议为带 complete、capabilities 与诊断的结构，不能把损坏流转换成空数组。

读操作可有限重试。写操作遇到可疑网络/服务器错误先标未知并核验，除非能证明远端未收到，不能使用统一重试包装器。

### 5.2 MoviePilot

用户已确认实际部署版本为 v2.15.6。对应版本应验证：媒体详情、豆瓣媒体搜索/详情、季集目、站点资源搜索、下载列表/状态、整理队列、完整历史分页、存储列表、预览、历史删除、手动整理。

API 返回形状集中在适配层处理，不能业务层各自猜 data/list/items。字段缺失或版本未知时形成兼容性错误。

上游 v2.15.6 兼容承诺不自动扩展到 v2.16 或 v3。公开 API 文档本次为 v3.1.9，需与用户部署分开；v2 的 source/带来源前缀 ID/裸响应，不能与 v3 的 media_source+media_id/业务包装混用。版本探测失败不得填写默认版本；只读取必要元信息，不收集完整环境变量。

接口按业务语义标记 read/preview/write。GET /transfer/now 等实际写操作不可用于只读探测，POST preview 也必须确认其对应版本语义。当前本地修复体中的 media_info/meta_info、overwrite_mode 与官方 v2 请求模型存在差异；服务是否接受、忽略或拒绝应实测，不得以未声明字段宣称不覆盖。详见 [接口研究](10-MoviePilot接口研究与接入方案.md)。

### 5.3 TMDB / 补查来源

日期不带时区时作为日历日期处理，结合统一核对时区；不转换成午夜 Date 后和当前秒比较。需验证 Gregorian 日期真实有效，例如 2026-02-30 不合法。

认证方式应由明确配置字段选择；日志只写不含密钥的路径与参数。不能把 api_key 查询串写入 info 日志。

Q-01 的业务触发已确认：默认 TMDB，本地可信集号在统一编号体系后超出其本季范围时用豆瓣复核。应在共用来源规则层实现，初检与复核复用，不能分别采用“文件数超出”和“集号超出”两种算法。动漫分部/绝对编号未映射时不能先判超范围。复核成功后保留双方证据、记录采用范围及理由，并重新计算缺集与版本完整性；不自动继承不适用的播完结论。

豆瓣接入已经确定为用户 MoviePilot v2.15.6：媒体搜索用 source=douban，详情用 /api/v1/douban/{doubanid}。该版本确有这些端点，但用户实例响应尚未实测。候选多义时可由用户指定豆瓣 ID，实际数据仍经 MP 获取；不以直连豆瓣作失败回退，不修改 MP 全局识别源。未完成必要复核时明确阻挡。MP 获取 TMDB 是可选适配方向，用户没有要求替换当前 TMDB 通道。

## 6. 报告协议与旧版兼容

Excel 是用户查看和人工维护入口；结构化状态库是执行依据。为离线交换可配套 JSON，但不得让“只有颜色”成为唯一身份和权限。

### 6.1 主表与明细

主表一“收藏范围 + 作品身份 + 编号体系 + 逻辑季”一行，可对应多个物理目录明细；剧级错误和电影/未知类别另列。基本列：记录 ID、范围 ID、profileId、配置版本、实际源根、contentKind、分类、剧名、媒体 ID、逻辑季号、物理路径、编号体系/映射、来源数量与证据类型、文件/集号事实、播期、工作流状态、阻挡原因、来源/文件核对时间、报告版本。

明细至少覆盖：文件快照、版本分析、下载、整理修复、复核计划、清理实际操作、归档操作、核验差异。本轮快照与旧明细追加关系明确，同一 runId 重复导出不重复叠加。

### 6.2 导入验证

- 检查文件大小、工作表结构、关键重复表头、合并关键格、公式关键字段、字段类型、schema。
- 正确处理工作表不是从 A1 开始的情况，不混淆相对表头索引与绝对列号。
- 云盘链接主机、配置 origin、路径字段、分类/剧名/季号应一致。
- 同一收藏/身份/编号体系的主表记录重复、跨表冲突或记录 ID 碰撞应阻挡相关写操作；合法多目录属于明细，不当作重复逻辑季。
- 已归档文字与颜色都能兼容识别，但任何冲突保持待核实。
- 无颜色的 CSV 仅用于查看/另行严格导入，不假装保留阶段语义。
- 外部表格为不可信输入，路径和机器记录不能直接变成执行请求。

### 6.3 字段迁移

| 上游/旧字段 | 本地当前字段 | 建议 |
| --- | --- | --- |
| 整理修复记录、整理修复记录续N | 修复记录、修复记录续N | 双读迁移到统一结构；同时存在且不一致时报冲突 |
| 整理修复状态/集号/时间/说明 | 修复状态/集号/时间/说明 | 统一内部状态，显示名称只作兼容映射 |
| 版本文件清单及续列 | 本地初检未输出完整对应字段 | 缺失时标版本不可核实，不能假造清单 |
| 下载/清理/归档明细 | 本地仅有限行字段 | 从操作日志生成新明细，旧表保留 |
| 颜色+中文处理结果 | 同类颜色和结果 | 导入为 legacy 状态，再核验事实；不直接授权 |
| 不含真实根、profileId、映射 ID 的旧报告 | showPath 由当前配置拼接 | 导入先绑定原库与真实路径；不能按新默认根重定向，动漫编号不明时禁止写 |

长 JSON 按单元格限制分片，携带分片数、总长度和摘要，读取校验完整性；禁止 slice 截断。新记录变短时清除旧续列，避免旧片尾残留破坏 JSON。

导出时使用临时文件与原子替换或唯一文件名；报告被 Excel 占用时明确错误，不覆盖旧文件。输出文件名不直接拼未经处理的用户关键词。

## 7. 命令与后台运行建议

以下均为未来接口方向，**当前 CLI 不保证存在**：

| 用户动作 | 建议行为 |
| --- | --- |
| inspect | 明确 scope；生成结果、范围和快照 |
| download plan | 只读检查并产生资源/修复计划 |
| repair plan | 仅检查整理问题 |
| review plan | 只读复核并列清理计划 |
| archive plan | 只读全量预检并列归档计划 |
| execute 指定 planId | 校验批准、锁与快照，执行具体计划 |
| verify / reconcile | 只读核验未决结果和归档清单 |
| resume 指定 runId | 恢复未完成范围，先解决未知请求 |

不要为兼容旧习惯让 verify 内含删除。若需要清理别名，独立生成 cleanup plan。

定时器必须明确时区、支持的表达式、启用状态、漏跑策略与单实例锁。当前只实现每日时分的简易解析，不能展示成完整 cron。应测试 00:00、睡眠恢复、时间跳变与任务跨日。

schedule.stages、transferRepair.enabled 等配置必须真正控制执行；无效字段启动时提示，不能给用户一种已禁用的假象。默认允许哪些自动写动作见 Q-05，未定案前不可开放隐式写权限。

## 8. 错误分类、日志与通知

建议错误码示例：

| 类别 | 示例 | 行为 |
| --- | --- | --- |
| 身份/数据 | IDENTITY_CONFLICT、SOURCE_UNKNOWN、REPORT_CORRUPT | 阻挡相关对象 |
| 读取 | AUTH_FAILED、LIST_INCOMPLETE、PATH_UNREACHABLE | 有限重试或人工处理；不转换为空 |
| 状态 | ACTIVE_TASK_UNKNOWN、REPAIR_PENDING、WRITE_UNCERTAIN | 只读核验，不再提交 |
| 计划 | SNAPSHOT_CHANGED、DEST_CONFLICT、SCOPE_MISMATCH | 计划失效并重新规划 |
| 写入 | PROVEN_NOT_SUBMITTED、PARTIAL_RESULT、POSTCONDITION_FAILED | 区分未发出与可能生效 |
| 本地持久化 | STORE_WRITE_FAILED、STORE_CORRUPT、REPORT_LOCKED | 写意图失败禁止外部提交；导出失败保留已执行记录 |

日志字段包括 runId、recordId、planId、operationId、阶段、动作、状态和时点。涉及 URL 时移除 token、api_key、passkey 与私密 enclosure；历史/响应采用白名单而非整对象打印。

摘要按单位分别统计：部、季、文件、请求、任务。不可把“修复 3 季”写成“修复 3 集”；统计应能由明细重算。

通知只报告实质变化：完成、部分失败、需人工、任务阻挡。未来后台轮询没有变化不重复通知；不能在 runAuto 吞掉错误后弹“全流程成功”。

## 9. 质量策略与可选扩展

建议先完成文件名/清单层闭环，再按实际需要增加内容探测、目标媒体库刷新、自动订阅、Web UI 等。每个扩展均不能改写已有核心规则。

测试分为纯规则、模拟适配器、故障注入、真实只读兼容性和获批的隔离写验证。后两者本次未执行；可重用已有接口能力但不承诺任何未核验版本。
